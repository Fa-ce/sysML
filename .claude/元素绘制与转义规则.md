# 元素绘制与转义规则

本文档用于指导任意前端项目实现：

- SysML v2 文本解析结果的前端转义
- 画布节点、边、端口、分区元素的绘制
- 多视图下的过滤、映射、样式与关系表达

目标是让后续项目即使脱离当前代码库，也能仅凭本文档实现一套可用、可扩展、语义正确的 SysML 前端绘图能力。

---

## 1. 适用范围

本文档适用于以下场景：

- SysML v2 文本建模工具的图形展示层
- SysML 模型浏览器、结构视图、互连视图、需求视图、行为视图
- 基于前端画布库的渲染实现
  例如：
  - X6
  - React Flow / XYFlow
  - G6
  - SVG/Canvas 自研画布

本文档不限定具体前端框架，但默认遵循：

- 代码即模型
- 图形是模型的投影
- 图形层不擅自改变模型语义

---

## 2. 最高准则

本规则以以下两份官方文档为最高准则：

1. `Intro to the SysML v2 Language-Textual Notation.pdf`
2. `Intro to the SysML v2 Language-Graphical Notation.pdf`

约束原则：

- 语法以 Textual Notation 为准
- 图形表达以 Graphical Notation 为准
- 若内部实现、历史文档、旧版本 UI 与官方 PDF 冲突，以官方 PDF 为准

---

## 3. 总体实现原则

### 3.1 代码唯一真源

前端绘图层必须遵循：

- SysML 文本是唯一模型真源
- 画布节点、边、端口、分区均为解析结果的投影
- 图形变化不应隐式修改模型语义

允许的交互：

- 选中
- 定位
- 居中
- 折叠/展开
- 视图过滤
- 局部布局
- 临时隐藏/高亮

不允许默认发生的行为：

- 用户拖动节点后自动反写 SysML 代码
- 删除画布节点后自动删除模型语义
- 创建一条图形边就自动生成文本模型语句

### 3.2 Definition / Usage 一致模式

SysML v2 中大量概念同时具有：

- Definition
- Usage

前端实现时必须保留这个双层语义，而不是把所有元素合并成单一类型。

示例：

- `part def` / `part`
- `requirement def` / `requirement`
- `action def` / `action`
- `state def` / `state`
- `port def` / `port`
- `item def` / `item`
- `interface def` / `interface`

### 3.3 视图优先于样式

前端实现优先级：

1. 概念语义正确
2. 节点/边映射正确
3. 视图过滤正确
4. compartment 结构正确
5. 端口与关系方向正确
6. 再处理视觉样式

不要把“卡片配色”优先级放在“关系语义”之前。

---

## 4. 前端绘图元素总分类

前端绘图层统一抽象为四类元素：

### 4.1 Node

表示可独立被识别、命名、选中、定位、展开的元素。

### 4.2 Edge

表示元素之间的方向、约束、依赖、连接、满足、流动、行为切换等关系。

### 4.3 Attachment

表示附着在节点或边上的结构点、端口、参数、端点信息、标签等。

### 4.4 Compartment / Member

表示节点内部的结构分区及其成员。

## 8. SysML 概念到前端类型的转义规则

### 8.1 Package

SysML 概念：

- `package`

前端转义：

- 转成 `package` 节点

语义：

- 命名空间
- 容器
- 结构组织

绘制要求：

- 具备 package 专属图形表达
- 支持折叠/展开
- 支持显示名称 tab 或名称头
- 可以容纳 members compartment

相关边：

- `containment`
- `import`
- `dependency`
- `expose`

### 8.2 Part

SysML 概念：

- `part def`
- `part`

前端转义：

- `part def` -> `partDef`
- `part` -> `partUsage`

语义：

- 结构主实体
- 系统组成部分

绘制要求：

- `partDef` 与 `partUsage` 风格可同族，但必须可区分
- 名称区必须存在
- 支持 ports / attributes / parts / perform / exhibit / relationships compartments

### 8.3 Port

SysML 概念：

- `port def`
- `port`
- `ref port`
- conjugated port

前端转义：

- `port def` -> `portDef`
- `port usage` -> `portUsage`
- 在 IBD 视图里常进一步转成 `Attachment.port`

关键规则：

- `port` 不是绝对只能画成边缘端口
- 在定义/说明图中，`portDef / portUsage` 可以是节点
- 在互连图中，优先作为节点边缘端口

绘制要求：

- 支持方向：`in / out / inout`
- 支持 conjugation `~`
- 支持端口名称和类型
- 支持挂接在节点四边

### 8.4 Interface

SysML 概念：

- `interface def`
- `interface usage`

前端转义：

- `interfaceDef`
- `interfaceUsage`

语义：

- 协议/连接语义容器

绘制要求：

- 可独立成节点
- 也允许在互连图中降为连接语义标签

### 8.5 Item

SysML 概念：

- `item def`
- `item usage`

前端转义：

- `itemDef`
- `itemUsage`

关键规则：

- `item` 是正式模型元素
- 不是只能做边标签
- 但在流图、消息图、端口图中可降级为边上语义对象

### 8.6 Connection

SysML 概念：

- `connection def`
- `connect`
- `binding`
- `bind`

前端转义：

- `connection def` -> `connectionDef` 节点
- `connect` -> `connection` 边
- `bind / binding` -> `binding` 边

关键规则：

- 定义与关系使用必须分离

### 8.7 Requirement

SysML 概念：

- `requirement def`
- `requirement`

前端转义：

- `requirementDef`
- `requirementUsage`

绘制要求：

- 保留 requirement 专属图形语义
- 支持 `subject`
- 支持 `require`
- 支持 `satisfy`
- 支持 `verify`
- 支持 requirement constraints / parameters compartments

### 8.8 Action

SysML 概念：

- `action def`
- `action`
- `perform action`
- `send`
- `accept`

前端转义：

- `actionDef`
- `actionUsage`
- `perform` -> 边或分区投影
- `send` -> 行为边
- `accept` -> 行为边

绘制要求：

- 行为图中使用专属动作节点表达
- 支持参数
- 支持 flow / succession / send / accept

### 8.9 State

SysML 概念：

- `state def`
- `state`
- `exhibit state`
- `transition`

前端转义：

- `stateDef`
- `stateUsage`
- `exhibit` -> 边
- `transition` -> 边

绘制要求：

- 状态图中支持子状态
- 支持 entry/do/exit
- 支持 state transition compartment

### 8.10 Control Node

SysML 概念：

- `start`
- `done`
- `merge`
- `decide`
- `fork`
- `join`
- `terminate`

前端转义：

- `controlNode`

关键规则：

- 不能当普通矩形节点处理
- 必须具备专属形状

### 8.11 Constraint / Calculation / Case / View

这些概念都属于正式节点类型：

- `constraintDef / constraintUsage`
- `calculationDef / calculationUsage`
- `caseDef`
- `analysisCaseDef`
- `verificationCaseDef`
- `viewDef / viewUsage`
- `viewpointDef / viewpointUsage`
- `renderingDef`
- `metadataDef`

实现要求：

- 不要求在第一版全部启用
- 但配置层必须预留
- 不允许未来继续靠临时字符串判断追加

## 9. 关系边的转义规则

### 9.1 containment

语义：

- 所属/包含关系

表达：

- 结构骨架主边
- 通常在 general 视图中最重要

### 9.2 specialization

来源：

- `:>`
- `specializes`

表达：

- 空心三角语义
- 表示一般化/特化

### 9.3 subsetting

来源：

- `subsets`

表达：

- 语义边

### 9.4 redefinition

来源：

- `:>>`
- `redefines`

表达：

- 语义边

### 9.5 dependency

来源：

- `dependency`

表达：

- 虚线依赖边

### 9.6 import / expose

来源：

- `import`
- `expose`

表达：

- 组织关系边

### 9.7 connection / binding

来源：

- `connect ... to ...`
- `bind a = b`

表达：

- 互连边
- 绑定边

### 9.8 flow / succession

来源：

- `flow`
- `first ... then ...`

表达：

- 行为或交互方向边

### 9.9 perform / exhibit

来源：

- `perform action`
- `exhibit state`

表达：

- part 与行为/状态之间的语义边

### 9.10 satisfy / require / verify / allocate

表达：

- 需求/验证/分析语义边

### 9.11 annotate

来源：

- `comment`
- `documentation`
- `textual representation`

表达：

- 注解边

## 10. Compartment 规则

官方图形表达里，compartment 是高优先级概念。

前端节点实现必须支持以下分区抽象：

### 10.1 Name Compartment

必须有：

- stereotype / kind
- short name（如有）
- full name
- type reference（对于 usage）

### 10.2 Members Compartment

可包含：

- attributes
- operations
- parts
- items
- ports
- actions
- states

### 10.3 Relationships Compartment

用于展示：

- specialization
- subsetting
- redefinition
- satisfy / require / verify
- variants

### 10.4 Specialized Semantic Compartments

例如：

- ports compartment
- perform actions compartment
- exhibit states compartment
- requirement constraints compartment
- verification methods compartment
- metadata compartment

结论：

- 前端不应把所有内容拍平到一个 label 文本里
- 必须为 compartment 预留抽象层

## 11. 视图策略

不同视图必须过滤不同语义，不允许一图通吃。

### 11.1 General

目标：

- 静态结构总览

默认显示：

- `package`
- `partDef`
- 必要时 `interfaceDef`
- 必要时 `requirementDef`
- `containment`
- `specialization`
- `dependency`

默认隐藏：

- `partUsage`
- `port`
- `binding`
- `flow`
- `transition`

### 11.2 IBD

目标：

- 部件互连

默认显示：

- `partUsage`
- `partDef`
- `port`
- `connection`
- `binding`
- 可选 `interface`

默认隐藏：

- 大量包层级
- 需求语义
- 行为语义

### 11.3 Requirements

目标：

- 需求及其满足/验证关系

默认显示：

- `requirementDef`
- `requirementUsage`
- `partDef`
- `partUsage`
- `satisfy`
- `require`
- `verify`

### 11.4 Behavior

目标：

- 动作、流、状态、转换

默认显示：

- `actionDef`
- `actionUsage`
- `stateDef`
- `stateUsage`
- `controlNode`
- `flow`
- `succession`
- `transition`
- `perform`
- `exhibit`
- `send`
- `accept`

### 11.5 View / Rendering

目标：

- 展示 `view / viewpoint / rendering`

默认显示：

- `viewDef / viewUsage`
- `viewpointDef / viewpointUsage`
- `renderingDef`
- `expose`
- `dependency`

## 12. 标准化配置结构

任意新项目必须落地为一份独立配置文件，建议命名：

- `sysml-mapping.ts`

结构至少应包含：

```ts
export const SYSML_FRONTEND_MAPPING = {
  nodes: {},
  edges: {},
  attachments: {},
  views: {},
  compartments: {},
};
```

### 12.1 nodes

每个节点类型至少配置：

- `family`
- `role`
- `defaultViews`
- `renderMode`
- `supportsCompartments`
- `supportsPorts`

### 12.2 edges

每个边类型至少配置：

- `family`
- `route`
- `defaultViews`
- `directional`
- `labelPolicy`

### 12.3 attachments

每个附着元素至少配置：

- `host`
- `renderAs`
- `viewPolicy`

### 12.4 views

每个视图至少配置：

- `nodeWhitelist`
- `edgeWhitelist`
- `attachmentWhitelist`
- `layoutPolicy`

### 12.5 compartments

每个节点族至少配置：

- `allowedCompartments`
- `memberKinds`

## 13. 实现约束

任意新项目必须满足：

1. 不允许仅靠零散 `if/else` 决定渲染语义
2. 必须有独立的 SysML 前端映射配置
3. 必须支持 Definition / Usage 区分
4. 必须支持多视图过滤
5. 必须支持节点、边、端口、compartment 四层结构
6. 必须支持官方 PDF 中明确的核心概念：
   - package
   - part
   - item
   - port
   - interface
   - connection
   - requirement
   - action
   - state
   - transition
   - flow

---

## 14. 新项目的实施顺序

建议严格按以下顺序实现：

1. 完成文本解析后的中间模型定义
2. 建立 `SysML 概念 -> FrontNodeType / FrontEdgeType / Attachment` 转义层
3. 实现 `General / IBD / Requirements / Behavior / View` 五类视图过滤
4. 实现节点基础壳体与 name compartment
5. 实现边语义与箭头/虚实线规则
6. 实现 ports 与 compartment
7. 最后再做主题、美化、交互动画

如果顺序反过来，通常会得到：

- 样式很好看
- 但语义完全不稳定

---

## 15. 最终结论

后续无论是否是当前项目，只要要实现 SysML 前端绘图，都应遵循本文档：

- 用官方 PDF 统一语法和图形语义
- 用配置驱动转义
- 用视图控制复杂度
- 用 compartment 保持专业表达

这样实现出来的系统，才具备跨项目复用价值。
